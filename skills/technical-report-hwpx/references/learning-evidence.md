# 기준 사례와 일반화 검증

2026-10-31에 사용자가 등록한 첫 기술진단 보고서 묶음에서 실제 분석한 범위다. 원본 파일·측정값·PDF 이미지는 이 스킬에 포함하지 않는다. 아래 관찰값은 이 사례의 근거이며 모든 보고서에 강제할 기본값이 아니다.

| 항목 | 확인된 사례 |
| --- | --- |
| 자료 구성 | HWPX 12개, 대응 PDF 12개 |
| 논리 장 | 6개: 1·2·3·6장은 공정·일반, 4장은 기계, 5장은 전기 |
| 분할 방식 | 1·2장은 한 파일, 3장은 6개 파일, 4장은 2개 파일 |
| 용지 | A4 210×297mm, 일부 구역 A3 297×420mm |
| HWPX 여백 | 좌우 25mm, 상하 15mm; 머리말/꼬리말 각 15mm |
| 반복 서체 후보 | 맑은 고딕 11pt, 휴먼명조 12pt 등 |
| 원본 개체 | 표 624개, 그림 394개. 배치용·계속 개체 포함 |
| 쪽 구성 | 앞부분 로마숫자, 본문 숫자; 장 구분 표지 다음 빈 쪽 사례 확인 |
| 저장된 단계 | 구조 분석·양식 후보·원본 근거 저장 |
| 미확정 단계 | 앱의 독립 페이지 재현, 전체 PDF 자동 대조, 다른 보고서로의 전이 검증 |

현재까지의 발견이 바꾸는 결정:

- 파일명 `1,2장`을 단일 장으로 분류하지 말고 본문의 두 장을 읽는다.
- `3.4`처럼 장 번호 없이 절만 있는 파일도 실제 본문 근거로 앞 파일의 3장에 연결한다.
- 계속 표의 반복 캡션을 새 표 번호로 증가시키지 않는다.
- 본문 구역을 A4로 일괄 변환하지 않는다.
- 머리말·꼬리말은 글자 외 선·도형을 포함할 수 있으므로 텍스트만 읽었다고 재현을 완료하지 않는다.
- 같은 서식의 문서라도 스타일 참조 ID가 달라질 수 있다. 반대로 같은 ID가 다른 서식을 가리킬 수 있다.

추가 보고서가 들어오면 위 숫자를 덮어써 공통 규칙으로 만들지 않는다. 사례별 분석을 보존하고, 일치하는 속성·달라지는 속성·필수 예외를 기록한다. 최소한 표지/장 구분 표지, 일반 본문, 병합 표, 그림·캡션, 빈 쪽, 용지가 다른 구역을 실제 검증 대상으로 고른다. 선택한 사례만 확인했다면 전체 보고서의 검증 완료로 확대하지 않는다.
# 한 쪽 재현시험 추가 관찰 (2026-10-31)

서남 프로젝트 개요·일반현황 파일의 PDF 1쪽, ‘제1장 기술진단의 개요’ 장 표지를 시험했다. HWPX와 정확히 일치하는 4개 글자 구간을 문단 근거와 연결하고, 이미지로 삽입됐던 회색 장식을 4개 편집 도형으로 수동 재구성했다. 글자 위치는 PDF 좌표에서 읽었다. 범용 HWPX 조판을 수행한 결과는 아니다.

HY헤드라인M을 설치 글꼴 이름만으로 지정하면 Chromium에서 대체되었고, 원본 TTF를 그대로 포함해도 cmap 검사에 실패했다. fontTools로 Unicode cmap의 언어값을 0으로 정규화한 글꼴을 로컬 편집 모델에 포함해 보정했다. 새 한글 입력을 위해 전체 Unicode 글리프를 유지한다. 서식 이름과 실제 출력 글꼴을 PDF에서 모두 확인해야 한다.

독립 출력된 PDF는 1쪽, 텍스트 일치, 래스터 이미지 0개, 글꼴 H2hdrM으로 확인했다. 144dpi 비교에서 밝기 차이 12 초과 픽셀 비율은 약 1.26%였다. 이 비율은 ‘재현 정확도’가 아니다. 원본 장식의 래스터 경계와 재구성 곡선·선 두께의 차이가 남으며, 용지 폭 약 0.26pt(0.092mm), 높이 약 0.08pt 반올림 차이가 있다. 상태는 `compared`이며 전체 보고서·복잡한 표·본문 자동 줄바꿈·홀짝 조판·HWPX 출력은 미검증이다.

앱의 합성 자료 시험에서는 다른 장 번호와 문구를 불러와 글자 및 도형 너비를 변경하고, 사용자별 저장·재시작 후 복구·원본 PDF 나란히 보기를 확인했다. 실제 보고서 편집본과 비교 산출물은 작업 저장소의 무시되는 `output/pdf/one-page-trial`에 보관하며 스킬 설치본에는 복사하지 않는다.


## PDF 단독 전기 작성 사례 (2026-10-31)

대청 전회 본보고서는 129쪽이며 대응 한글 원본 없이 검사했다. 텍스트·장 제목·표 경계로 공통 20쪽, 공정 28쪽, 기계 50쪽, 전기 31쪽(장 표지·빈 쪽 포함)을 분류했다. 표 영역 95개·그림 후보 82개는 구조 탐지 수이며 최종 표/그림 캡션 수가 아니다. 일부 본문은 글자 대신 얇은 JPEG 띠이므로 텍스트 추출만으로 전체 본문을 분석했다고 판정할 수 없다.

103쪽을 대표 검사로 선택했다. 한국어 OCR로 이미지 본문 1줄을 보강하고 가로로 나란한 사진 3개, 본문·캡션·점검표를 새 HWPX에 썼다. 실제 한글 2020에서 문자·표와 3개 사진의 같은 행 배치를 확인했다. 원본과 동일한 쪽 배치 재현을 검증한 것은 아니다. 금회 양식은 항목 열을 유지하고 과거 수치·판정을 비웠으며 신규 빈 셀에 기존 문서 교체 엔진으로 측정 문자열을 넣는 것을 검사했다.

별도 시험 계정에서 원본 바이트 유지, 추출 셀 수동 보정의 저장·출력 반영, 출력 서식 저장, 프로젝트 전환 격리를 확인했다. PDF.js 원문 캔버스 표시·한국어 OCR·신규 HWPX 생성은 개발 서버뿐 아니라 Electron의 로컬 file:// 배포 빌드에서도 통과했다. 전기 31쪽 전체의 OCR 정확도·최종 진단 문구·다장 조판·전체 홀짝 정책은 아직 이 사례로 검증하지 않았다. 프로젝트 원본·측정값·생성물은 스킬에 포함하지 않는다.

## 복원 편집 작업 검증 (2026-11-03)

같은 PDF의 전체 분석과 103쪽의 원문·복원 구조 나란히 보기, 복원 문장·표 셀 수정, 교체 자료 결정 저장, 사진 3개 표시와 HWPX 반영을 개발 서버와 로컬 파일 실행에서 검사했다. 이때 생성한 HWPX의 새 서식과 최종 쪽 배치를 실제 한글에서 다시 출력 대조한 것은 아니다.

합성 HWPX에서는 풍부한 머리말의 글자·표·그림·도형 원본 보존, 본문 스타일 복제와 용지 여백 변경, 개체 위치 변경, 공유 그림 중 선택 개체만 교체하는 것을 구조 검사했다. 브라우저에서는 서식 편집·프로젝트 사진 등록·교체 후보 결정·별도 후보 생성·후보의 새 원본 해시로 재분석·프로젝트 파일 복구를 확인했다. 사진 등록 때문에 보고서를 재분석하며 편집 상태가 사라지던 현상을 수정했다. 이 결과는 임의 PDF 도형의 완전 복원이나 범용 한글 조판 검증을 의미하지 않는다.

## 프로젝트 플랫폼에서의 분석·한글화 (2026-11-03)

사용자 요청으로 별도 PDF·HWPX 학습 실험을 멈추고 먼저 프로젝트 플랫폼을 구현했다. 새 기본 화면의 브라우저 검사 26개에서 전회 보고서와 금회 자료의 분리, 명시적 분석 후 한글화 활성화, 표·그림·데이터 관리, 그림 미리보기, 내용 역할·교체 결정·근거자료 연결, 역할별 서식의 실제 HWPX 반영, 원문 PDF 연결 상속, 프로젝트 격리와 파일 복원을 확인했다. 해시가 다른 분석의 복원을 거부하고, 다른 프로젝트로 복원할 때 분석의 귀속을 바꾸는 것도 검사했다.

이 플랫폼 안에서 129쪽 실제 PDF를 OCR 없이 분석하고 103쪽을 선택해 편집 가능한 본문·표가 있는 HWPX 후보를 생성했다. 이미지 글자 영역은 인식하지 않고 원문 그림 조각으로 보존했다. 원문은 그대로 보관하고 후보를 별도로 등록해 PDF 연결을 확인했다. 이 실행에서 원래 한글 원본과의 대조 학습이나 새 후보의 실제 한글 출력 검증까지 마친 것은 아니다.

기존 보관 작업의 브라우저 회귀 검사 31개도 통과했다. 이 중 이전 화면의 자동 분석·폴더·목차 항목은 호환성 검사용이며 새 기본 화면의 작업 순서로 되돌리지 않는다. 좌우 너비 조절·자동 배율·반응형 설정·너비 기억 검사를 포함한다. 단위 검사 164개와 제품 빌드도 통과했다. 검증 수는 이 작업 버전의 범위를 기록한 것이며 임의 보고서의 복원 품질 보장이 아니다.

같은 날 사용자가 PDF 중앙의 불필요한 설명·버튼을 제거하고 연속 스크롤을 요청했다. `PdfContinuousView`를 연결한 뒤 새 플랫폼 검사를 36개로 확장해 통과했다. 합성 3쪽 문서에서는 스크롤에 따른 현재 쪽·저장값, 고정된 제목/페이지 바, 번호 입력·이전/다음, 범위 밖 입력 거부, 자료 탭·프로젝트 전환 뒤 쪽 복귀를 확인했다. 실제 129쪽 문서는 64쪽 바로가기에서 화면 근처 쪽만 캔버스를 할당하고, 사이드바 조절 후 너비 맞춤과 현재 쪽을 유지했다. 최종 화면에서 103/129 표시와 원문을 시각 확인했다. 페이지 읽기 UI의 검증이며 HWPX 출력 재현의 검증 범위를 확장하지 않는다.

## 복원 분석과 작성 분석의 분리 (2026-11-03)

사용자는 분석의 목적이 페이지 구조를 명확히 파악하고 재현·재사용할 수 있는지를 판단하는 것이라고 정리했다. PDF 복원 분석 → 한글화 → 새 보고서 작성 분석과, 기존 한글의 직접 작성 분석을 구분했다. 중앙은 미리보기/분석보기이며 분석보기는 챕터별 개체·제목·서체·페이지 요약을 먼저 연다. 챕터 선택은 오른쪽 수정 화면에 연결한다.

현재 분석 버전은 `report-workflow/2`이다. 기본 흐름 34개, 실제 PDF 포함 흐름 39개와 단위 검사 165개를 통과했다. 새 검사에서 PDF에는 작성 결정이 노출되지 않고, 한글 원본은 작성 분석으로 진입하며, 챕터 선택·보정 저장·해당 범위의 표 글자 서식 후보 생성과 프로젝트 파일 회수를 확인했다. 두 장을 가진 합성 HWPX에서는 첫 장 본문 글자 서식을 바꿔도 둘째 장과 공유 머리말의 글자 모양 참조를 유지했다. 머리말 문단을 본문 범위로 위장한 요청은 거부했다.

HWPX에서 실제 쪽 수를 아직 확정하지 못하는 범위는 미확인으로 표시한다. 원본 조판과 다른 추출 HTML은 기본 미리보기에서 제거했고, 기존 원본의 대응 PDF와 후보의 실제 출력 미리보기를 구분한다. 챕터 요약·편집 화면을 시각 확인했으나 임의 한글 문서의 조판 엔진이나 복원 후보의 실제 한글 출력 재현을 완료한 것은 아니다.

## 분석 항목과 원문 위치의 왕복 (2026-11-03)

표·그림·문단에서 원문을 확인한 후 돌아오기 위해 관리 화면을 유지하고 원문 항목 ID·보고서 SHA·스크롤 위치를 일시 보관한다. PDF 표·그림은 실제 쪽과 원본 좌표 영역을 표시한다. 한글은 표/셀·문단·그림의 원본 구조 ID로 항목과 주변 문맥을 열며 그림은 원본 패키지의 자산을 읽는다. 이 한글 위치 보기는 실제 페이지 조판의 재현을 의미하지 않는다.

기본 플랫폼 화면 검사 46개에서 PDF와 HWPX 항목의 원문 이동, 떠 있는 복귀 버튼, 관리 탭·챕터 필터·펼친 그림·스크롤과 키보드 초점·챕터 서식 대상의 보존을 확인했다. 원문 표 화면과 복귀한 표 관리 화면을 시각 확인했다. 원문 표의 셀 선택과 금회 자료 반영 경로를 함께 유지한다. 다른 보고서나 프로젝트로 전환할 때 이전 원문 이동 상태를 노출하지 않는다.

## 장 카드 선택과 장별 HWPX 등록 (2026-11-03)

사용자는 분석한 장을 하나씩 선택해 한글화하고 보고서 목록에서 해당 장의 미리보기·작성 분석으로 이어지는 흐름을 요청했다. PDF 분석 직후에는 선택을 비워 두며 카드 재클릭으로 해제한다. 선택 장의 페이지를 원본 SHA·프로젝트·분석 장 소유 관계와 검증하고 공백 쪽을 포함해 변환한다. 수동 전체 쪽 설정이 다른 장을 끌어들이지 않는다. 장별 출처는 프로젝트와 HWPX 패키지 안에 보존한다.

두 장·중간 공백 쪽을 가진 합성 PDF에서 첫 장과 둘째 장이 서로의 내용을 포함하지 않는 HWPX로 등록되는지 검사했다. 생성한 바이트를 다시 읽어 작성 분석을 자동 저장하며 목록 재선택·프로젝트 저장/복원 뒤에도 장 범위와 분석을 유지했다. 장 미리보기는 해당 원본 PDF 페이지만 표시하고 장 안의 순번과 원본 페이지를 연결했다. 기본 흐름 54개에 실제 129쪽 PDF의 연속 보기·너비 조절·OCR 없는 분석·103쪽을 포함한 장 전체 한글화·원본 연결 검사 5개를 더해 화면 검사 59개가 통과했다. 생성본의 챕터 분석 요약과 오른쪽 편집 화면을 시각 확인했다. 단위 검사 168개와 제품 빌드도 통과했다.

이 결과는 한글 파일의 실제 내용을 읽는 미리보기 경로에 대한 검증이다. 모든 원본 PDF의 위치·글꼴·도형을 동일하게 복원했거나 한컴 프로그램의 실제 출력과 완전히 일치한다고 판정한 것은 아니다. 화면의 페이지 수는 연결 PDF나 단순 명시 나눔 개수가 아니라 해당 렌더러의 조판 결과이며, 한컴 출력과의 차이는 계속 검토한다.

## 흐린 중복 글자와 장 표지 보정 (2026-11-03)

사용자는 재생성 후에도 조판이 다르고 글자가 그림처럼 흐리다고 지적했다. 실제 서남 개요·일반현황 34쪽 PDF와 HWPX 쌍을 점검했다. PDF의 본문은 추출 가능한 텍스트다. 장 표지 배경은 4개 이미지 타일이며 그 안에는 표지 글자가 없다. 기존 `cropPdfPictures`는 전체 쪽을 1.6배 렌더링해 bbox로 잘랐으므로 배경 위의 실제 글자까지 PNG로 찍고, 작성기는 같은 글자를 다시 본문으로 넣었다. 생성 HWPX 자체의 독립 미리보기에서 흐린 글자와 선명한 중복 글자가 동시에 보이는 것을 재현했다.

## 대청 본문 이미지와 서체 미확정 (2026-11-03 추가 관찰)

사용자가 표 안 글자는 선명하지만 본문이 흐리다고 제시한 화면은 대청 PDF 119쪽의 감시제어설비 기본 기능 부분이다. 원본 쪽에는 높이 127픽셀의 글자 이미지 개체 24개가 있으며 같은 줄의 이미지가 겹치기도 한다. 해당 본문 두 문장은 PDF의 실제 글자 추출과 그리기 trace에 없고, 표·소제목·캡션은 글자로 추출된다. 문장 식별 시 ‘감시제어설비가’만 검색하면 표 캡션에 일치하므로 ‘감시제어설비가 효율적으로’ 등 문장 단위로 검증해야 한다. 전체 보고서가 스캔 문서라는 뜻은 아니며, OCR을 자동 추가하지 않는다.

비교용 대청 HWPX에서도 해당 본문 문장이 편집 문단으로 확인되지 않았고, 1,036개 내장 그림이 있다. 이 파일의 본문/표 서체 집계만으로 이미지 본문의 원래 글꼴을 확정하지 않는다. PDF의 CIDFont+F1/F2 같은 이름도 원래 설치 서체 이름으로 확정하지 않는다. 선명한 표 글자도 원본 서체 일치의 증거가 아니다. 원본 119쪽 표는 회색 머리행·흰 글자·가운데 정렬인데 사용자 생성본 캡처는 흰 머리행·검은 글자·왼쪽 정렬로, 셀 색상·정렬 복원도 남아 있다. 원본 이미지 품질 보존, 편집 가능한 본문 복원, 원래 글꼴 확정은 각각 검증한다.

## 원본 쌍의 본문 한 쪽 재작성 시험 (2026-11-03)

사용자 요청에 따라 서남 단위공정 운영 보고서의 PDF 파일 20쪽(인쇄 54쪽)을 선택했다. 원본 HWPX의 `section1.xml`에서 검토한 최상위 문단 범위는 157~165이며 한 구역 전체를 한 쪽으로 잘라내지 않았다. 본문 휴먼명조 12pt, 표·캡션의 맑은 고딕과 머리말 HY울릉도M 등 원본 글자·문단·셀 스타일을 재사용하고, PDF 텍스트 64개 구간을 연결해 새 한 쪽 HWPX를 작성했다. 단위와 표 아래 주석 두 문구는 PDF의 텍스트 추출에 없으므로 원본 HWPX 및 PDF 시각 대조 근거를 별도 해시 결합 JSON으로 남겼다. 그래프 두 개는 원래 그림 개체를 보존했다. 이 방식은 원본 HWPX의 서식·배치를 활용한 템플릿 재작성 시험으로, PDF 단독 자동 복원과 구분한다.

문서 상속 상태를 검토해 앞 구역의 `hp:pageNum`을 포함했고, 인쇄 쪽 54는 `hp:newNum numType="PAGE" num="54"`로 다시 시작했다. header beginNum/secPr startNum만으로 현재 렌더러 쪽 번호는 바뀌지 않는 것을 확인했다. 그림 배치용 표 문단에 빠진 줄 배치 캐시는 앞뒤 문단·표 크기·외부 여백과 PDF 좌표로 검토한 값만 보충했다. 원본 그림과 실제 HWPX 후보 바이트를 별도 로컬 렌더러로 출력했다. 본문/셀 수정 후 다시 파싱해 변경이 적용되고 그림 자산이 유지되는 것을 확인했다. 데이터 표 10행×6열 60셀, 그림 2개, 한 쪽 및 쪽 번호 54, XML 유효성과 원본 해시 보존을 검사했다.

실제 한글 UI 연결은 native pipe 부재로 사용하지 못했다. 독립 뷰어의 머리말 기준선·그림 캡션에 약 3pt 차이가 남고, 꼬리말 장식선의 배치 및 표선 렌더링도 원문과 달라 `compared`, `hancomOutputVerified:false`로 유지한다. 후보 XML의 용지 크기로 PDF media box만 보정했고 내용 스트림·글자 좌표·이미지를 원본 PDF에서 복사해 대체하지 않았다. 변경 픽셀 비율이나 유효한 ZIP만으로 동일 재현 합격을 선언하지 않는다. private 결과는 `output/pdf/one-page-reproduction/`에 보관하고 원문·폰트·결과 파일을 스킬에 넣지 않는다.

사용자는 이 후보를 한글에서 열었을 때 잘 재현된 것 같다고 확인했으나 대조 그림의 세로 위치 차이를 지적했다. 이는 사용자 시각 관찰이며 한글에서 내보낸 PDF의 좌표 검증은 아니다. 재측정 과정에서 Chromium의 둥근 용지 높이를 원래 높이로 바꾸면서 media box의 아래쪽 원점을 0으로 고정해, 대조용 출력 전체가 약 0.88pt 위로 이동하는 문제를 확인했다. PDF의 좌표는 아래쪽에서 시작하므로 보정 시 위쪽 경계와 왼쪽 경계를 보존하도록 수정했다. 합성 PDF의 글자·선 좌표와 내용 스트림이 유지되는 것을 검사했다. HWPX 바이트는 바꾸지 않았다.

수정 후 같은 용지 원점에서 본문 제목·첫 줄·표 제목·두 그래프의 세로 위치 차이는 0.02mm 이내였다. 독립 뷰어의 머리말은 약 0.98mm 위, 그림 캡션은 약 1.01mm 아래, 꼬리말 장식선은 약 4.59mm 아래에 남는다. 전체 쪽 이동과 개별 개체의 조판 차이를 구별하며, 이 뷰어 오차를 숨기기 위해 HWPX 좌표나 비교 이미지를 이동하지 않는다. 실제 한글 출력과의 판정에는 후보를 한글에서 내보낸 PDF가 필요하다. 재측정 근거는 private 결과의 `comparison/position-audit.json`에 원본·후보 해시 및 용지 위쪽 기준 좌표로 남긴다.

## 실제 앱의 HWPX 생성 경로 보강 (2026-11-03)

후속 대청 회귀 검증에서는 인쇄 104쪽의 일부 본문이 원본 PDF 자체에서 24개의 이미지 조각으로 저장된 것을 확인했다. 이전 엔진은 작은 조각을 누락하거나 줄 흐름으로 배치해 글자가 잘리고 원문 31쪽인 제5장 후보가 34쪽으로 늘어났다. 좁은 조각을 유지하고 텍스트·표·그림의 원문 좌표를 네이티브 개체에 적용했다. 장식의 직사각형 클리핑, 회색 그라데이션 띠와 꼬리말 선도 추가했다. 긴 표만 있는 125·126쪽에서도 흐름 배치가 쪽을 늘리는 문제가 있어 같은 원문 좌표 배치 경로로 처리했다. 최신 앱 경로에서는 원문 99~129쪽 31개와 독립 뷰어의 31쪽이 대응한다.

대청 머리말은 내장 폰트 이름에서 HY견고딕을 식별했으며 검정과 회색 텍스트 겹 사이에 가로·세로 약 0.96pt 차이가 있었다. glyph 좌표와 페인트 순서를 읽어 ‘용역(대청)’의 괄호·한글 순서를 보존하고 두 겹을 편집 가능한 글자 개체로 작성했다. 원래 글맵시 변형과 외곽선·그림자의 편집 설정 전체가 복구된 것은 아니다. 익명 CID 표 글꼴은 미확정으로 남아 기본 글꼴을 쓰는 셀이 있으며, 이를 글꼴 일치 합격으로 보지 않는다. 이미지 본문은 원본 픽셀로 유지하고 OCR 없이 편집 가능한 글자로 바뀌었다고 표시하지 않는다.

문단 스타일 분석·편집에는 좌우 들여쓰기, 첫 줄 들여쓰기/내어쓰기, 문단 위아래 간격, 문단 정렬과 줄 나눔 플래그를 추가했다. 네이티브 HWPX의 실제 설정과 스타일 참조를 읽고 선택한 문단 모양만 복제한다. 강제 줄바꿈과 인접 문단·공유 머리말을 보존하고 수정 문단의 낡은 줄 배치 캐시를 제거하는 검사, 챕터 UI에서 3mm 왼쪽 들여쓰기와 -2mm 내어쓰기를 실제 HWPX에 쓰고 다시 읽는 검사를 통과했다. 복원본의 비어 있는 페이지 앵커에 속한 그림은 실제 하위 문단의 챕터로 연결해 잘못된 ‘장 미분류’ 카드를 만들지 않게 했다.

최신 단위 검사 194개, 실제 대청 PDF 포함 기본 플랫폼 검사 85개, 설치 방식의 로컬 file 플랫폼 검사 78개와 프로덕션 빌드를 통과했다. 실제 사용자 프로젝트 저장소를 바꾸지 않는 격리 검사다. 한글 프로그램에서 직접 확인한 결과는 아니므로 `hancomOutputVerified:false`를 유지한다. PDF의 줄별 좌표 재현과 원래 여러 줄 문단 묶음·강제/자동 줄바꿈 판별은 별도 과제다. private 한 쪽 후보는 `output/hwpx/daecheong-page104/`, 앱에서 만든 장 전체 후보와 검사 로그는 `.firebase/`에 있다. 기존 서남 한 쪽 시험 HWPX는 수정하지 않았다.

사용자는 최종 목표를 한글에서 편집 가능한 HWPX의 재현으로 확정하고 PDF는 한글에서 만들 수 있다고 지시했다. 이후 점검은 대조 PDF·독립 뷰어의 오차 보정보다 HWPX 패키지 자체를 우선했다. 한 쪽 시험용 원본 HWPX 템플릿 재작성과 앱의 PDF 단독 새 패키지 생성은 별도 경로임을 유지한다.

`pdf-structure/3`에서 사각형 단색 채움·텍스트 페인트의 단일 색·선의 색/굵기/점선을 추출하고, 셀 텍스트와 정확히 연결되는 색만 사용한다. 곡선·패턴·투명 채움과 혼합 글자색을 단색으로 추정하지 않는다. 바깥 세로선이 없는 표도 긴 가로선의 끝 좌표를 열 경계로 사용한다. 원문 좌표에서 좌/중/우 정렬을 추정해 검토 속성으로 남기고, `pdf-hwpx/3`에서 셀 채움·글자색·각 변의 선과 짧은 원래 행 높이를 실제 한글 속성으로 작성한다. 열 너비의 반올림 합계를 맞추고 누락/중복 병합 셀은 저장 전에 거부한다. 표·그림 제목의 근거 있는 서체·크기·색·굵기도 유지한다.

복원 후보는 선택한 원문 쪽마다 HWPX 구역을 만들고 공유 서식, section manifest/spine, 쪽별 용지·머리말·꼬리말을 함께 기록한다. 공백·장 표지의 첫 쪽에는 머리말·꼬리말·쪽 번호 숨김을 적용한다. 실제 인쇄 번호는 `newNum`으로 시작하며, 마지막 45pt보다 위에 있는 숫자도 본문 표 밖의 하단 번호이면 읽는다. 번호 없는 쪽에는 임의 번호를 보이지 않게 하며 앞 구역의 번호가 상속되는 것도 숨긴다. 이전 PDF 분석에는 이 근거가 없으므로 앱의 한글화 버튼에 재분석 안내를 연결했다. 기존 HWPX 후보와 사용자 프로젝트 저장소는 변경하지 않았다.

합성 PDF의 회색 머리행/흰 글자가 실제 한글 셀 속성에 도달하는지 기본 플랫폼과 로컬 file 실행에서 검사했다. 표 셀 수정·재파싱, A4/A3 혼합 용지, 서로 다른 쪽별 머리말, 공백 쪽, 54→55→56의 네이티브 번호 재시작을 검사했다. 실제 서남 20쪽 PDF를 OCR 없이 앱에서 분석해 장별 HWPX 등록·직접 미리보기까지 수행했다. 인쇄 54쪽은 10행×6열 60셀을 유지했고 생성 문서에는 원문 쪽과 대응하는 20개 구역이 들어 있다. 네이티브 뷰어에서도 20쪽으로 조판됐으나 이를 실제 한글 출력의 정밀 재현 검증으로 취급하지 않는다. 단위 검사 187개, 실제 보고서 포함 플랫폼 검사 83개와 로컬 file 플랫폼 검사 77개를 통과했다. 본문은 아직 흐름식 조판이며 혼합 글자 모양·장평/자간의 정확한 역추정, 복잡한 도형과 임의 보고서의 동일 쪽 배치에는 추가 작업이 필요하다.

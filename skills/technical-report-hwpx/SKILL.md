# 기술진단 보고서 형식 분석·재현

목표는 한 보고서의 내용을 암기하는 것이 아니라 **원본 읽기 → 형식 규칙 추출 → 편집 가능한 작성본 생성 → 원본 PDF와 대조 → 보정** 절차를 다른 보고서에도 적용하는 것이다. 원본과 근거 위치를 보존하고, 보고서별 관찰값과 사용자가 요구한 편집 규칙을 구분한다.

## 요청에 맞는 작업 선택

- 폴더 분석·양식 학습: `scripts/analyze-project.mjs`로 파일별 구조와 논리 장, 서식 후보를 추출한다. 앱에서 이미 등록한 자료라면 `referenceLearning.js`의 같은 분석 엔진과 저장 경로를 사용한다.
- 기존 양식으로 작성: `scripts/write-candidate.mjs`로 해시와 정확한 글자 구간을 지정해 내용을 교체한다. 이미지·서식·표 구조는 원본 패키지에서 보존한다. 입력항목과 판정 셀의 연결 규칙은 [작성·재현 계약](references/reproduction-contract.md)을 읽는다.
- 재현 검증: 독립적으로 생성·내보낸 후보 PDF를 `scripts/compare-pages.py`로 원본 PDF와 비교한다. 이미지와 텍스트·쪽 구성을 함께 검토한다. 기존 PDF를 그대로 복사하거나 배경 이미지로 붙여 만든 결과는 편집 가능한 재현의 증거가 아니다.
- 한 쪽 보조 시험: `scripts/extract-page-trial.py --pdf <원본> --hwpx <원본> --font-map <글꼴연결.json> --decorations <검토한도형.json> --output <편집페이지.json>`으로 위치와 문단 근거를 연결한다. 글꼴 포함이 필요하면 `--font-file family=path`를 사용한다. 생성 JSON은 앱 왼쪽 ‘한 쪽 재현시험’에서 불러온다. 자동 조판 성공으로 취급하지 않는다. 자세한 지원 범위와 출력 명령은 앱 연결 지점을 따른다.
- 앱 기능 개발: [앱 연결 지점과 현재 능력](references/app-integration.md)을 읽고 기존 파서·워커·원본 작성기를 재사용한다.

## 학습해야 하는 것

문서별로 표지·속표지·제출문·책등·차례·장 구분 표지·본문·부록을 찾는다. 파일 하나에 여러 장이 있거나 한 장이 여러 파일로 나뉠 수 있으므로 파일 개수·파일명만으로 장을 확정하지 않는다. 파일명과 실제 본문이 다르면 본문 근거를 표시하고 사용자의 수동 분류를 임의로 덮어쓰지 않는다.

용지·구역·여백·서체·글자 크기·행간·문단 들여쓰기·표 셀 병합·그림과 도형 배치·머리말·꼬리말·쪽 번호·표/그림 번호를 원본의 구역·문단·글자 구간 및 SHA-256과 연결한다. 스타일 ID는 문서마다 다른 로컬 참조이므로 보고서 간에 ID 숫자만으로 동일 서식을 판단하지 않는다. PDF의 인쇄 여백·재단 영역과 HWPX의 용지 크기도 구분한다.

이전 보고서의 시설명·날짜·측정값·판정·결론·법령은 서식 규칙이 아니다. 새 보고서 값으로 자동 재사용하지 않는다. 사용자가 지정한 로고·표지 그림 등의 자산만 재사용한다. 원본에 있는 오타나 번호 오류도 양식 규칙으로 확정하지 않는다.

## 이 사용자의 보고서 규칙

- 새 장과 본문의 시작은 홀수 쪽이다. 앞 장이 홀수 쪽에 끝나면 짝수 빈 쪽을 삽입한다. 이 빈 쪽에는 머리말·꼬리말·쪽 번호를 모두 숨긴다. 구역의 `pageStartsOn` 값만으로 실제 PDF의 홀짝 배치가 맞다고 판정하지 않는다.
- 점검표의 빈 양식은 왼쪽 항목 목록을 유지하고 오른쪽 판정 부분만 비운다. 작성해 돌아온 양식은 원본 버전과 셀 위치를 확인한 뒤 같은 표·같은 셀에 반영한다.
- 공정은 기계·전기를 제외한 나머지를 포함한다. 기계·전기는 실제 장 제목과 내용 근거로 분리하며, 항상 4장·5장이라고 가정하지 않는다.
- 표·그림 번호는 논리 장과 분할 파일의 연속성을 고려한다. 배치용 표, 계속 표, 본문 참조와 실제 캡션을 구별한다.
- 편집 플랫폼은 왼쪽 목차·챕터, 가운데 편집 가능한 페이지, 오른쪽 머리말·꼬리말·제목·표지 설정을 사용한다. 원본 참고자료와 새 입력자료를 분리한다.

## 실행 예

아래 `scripts/`는 이 `SKILL.md`가 있는 디렉터리를 기준으로 한다. 다른 작업 폴더에서 실행할 때는 실제 스킬 경로를 붙인다.

스크립트는 Node와 이 앱 저장소의 의존성을 사용한다. 현재 작업 폴더 또는 스킬 위치에서 저장소를 찾고, 다른 환경에서는 `--repo`로 지정한다. 폴더 분석은 `inspect-pdf.py`로 PDF의 실제 쪽 수·용지·빈 쪽 근거도 읽는다. 이 작업에는 PyMuPDF가 필요하며, 준비되지 않았다면 `--skip-pdf`로 미검사 상태를 명시한다. PDF 비교에는 추가로 Pillow가 필요하다. 사용자의 원본과 생성물은 스킬 폴더에 복사하지 않는다.

```text
node scripts/analyze-project.mjs --repo <앱 저장소> --input <보고서 폴더> --output <분석 결과.json>
node scripts/analyze-project.mjs --repo <앱 저장소> --input <한 파일.hwpx> --output <분석 결과.json> --slots
node scripts/write-candidate.mjs --repo <앱 저장소> --source <원본.hwpx> --edits <교체 계획.json> --output <작성 후보.hwpx>
python scripts/compare-pages.py --reference <원본.pdf> --candidate <작성 후보.pdf> --reference-page 3 --candidate-page 3 --candidate-source <작성 후보.hwpx> --output <비교 결과 폴더>
```

교체 계획은 `sourceSha256`과 `replacements` 배열을 가진다. 각 항목은 분석의 `editableSlots`에서 얻은 `slotId`, `expectedText`, 새 `value`를 지정한다. 원본 자체에 출력하지 않는다. 글자 길이가 달라지면 한글에서 줄바꿈·셀 높이·쪽 나눔을 다시 계산하고 후보 PDF를 내보낸다.

## 완료 판정과 일반화

`extracted`는 형식 후보 추출, `candidate-generated`는 편집 가능한 후보 작성, `compared`는 원본과의 비교 자료 생성이다. `verified`는 편집 가능성·내용·배치·홀짝·표와 그림 번호가 실제로 확인된 범위에만 사용한다. 텍스트 추출 성공, 유효한 ZIP, 단순 이미지 유사도만으로 재현 완료라고 말하지 않는다.

현재 엔진은 HWPX 구조 추출과 기존 패키지의 글자 구간 교체, 프로젝트에 귀속된 PDF의 분야/표 구조 분석 및 전기 HWPX 신규 작성을 지원한다. PDF의 이미지 본문은 로컬 한국어 OCR로 보강할 수 있으며 낮은 신뢰도·미인식·병합 셀은 검토 대상으로 유지한다. 새 HWPX는 텍스트·표·부분 그림으로 구성하고 PDF 전체 쪽을 배경 그림으로 붙이지 않는다. 신규 작성과 원본과 동일한 쪽 배치 재현은 다른 완료 기준이다. 가운데 편집화면에서 임의의 한 쪽을 독립적으로 구성해 원본과 동일하게 재현하는 범용 조판기는 아직 검증되지 않았다. 이 한계를 문서만으로 완료 처리하지 않는다.

기준 보고서의 관찰값은 [기준 사례와 일반화 검증](references/learning-evidence.md)에 있다. 다른 유형의 보고서에도 적용할 때는 그 보고서를 별도 검증 자료로 삼아 성공한 범위와 실패 사례를 기록한다. 한 프로젝트에서의 성공을 모든 보고서에 대한 보장으로 확대하지 않는다.

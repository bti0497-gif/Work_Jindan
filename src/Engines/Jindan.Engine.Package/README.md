# Native package boundary66

This net10.0/BCL-only independent DLL is the first limited C# engine promotion. It performs read-only ZIP/HWPX inventory, secure XML counts/manifest checks, SHA256, and project-assisted recovery verification. PDF analysis, faithful HWPX layout/restoration, existing binding/draft semantics and raster/font handling remain **Hybrid/JS**, not a rewritten or simplified C# renderer. The DLL has no WinForms/Contracts/Node/NuGet dependency.

API:

```csharp
NativePackage.InspectHwpx(bytes, limits: null, validateManifest: true, ct);
NativePackage.VerifyRecovery(bytes, projectId, expectedSha256, ct);
```

Results include entry content SHA/length, section paragraph/text-slot/cell/picture counts and canonical slot text SHA. No caller bytes are changed or saved. HWPX accepts at most160MiB compressed,20,000 exact case-sensitive ZIP names,256MiB expanded,48MiB XML; explicit limits can reduce but cannot exceed the declared upper bounds. Traversal/absolute/backslash/colon/control-character paths, exact duplicates and signed/encrypted names are rejected before extraction. Entries stay in memory: there is no filesystem extraction. XML uses DtdProcessing.Prohibit, XmlResolver=null and character limits. OPF checks unique IDs, existing package targets, sections and spine references; package-relative hrefs are resolved inside the virtual package root. This is structural validation, not the full Hancom XSD, layout, original font or editing approval.

Repair66 JS and C# use the same frozen synthetic goldens under tests/Jindan.NativeEngine.Tests/goldens. Normal generated HWPX has2 sections,4 cells and1 PNG; expected every-entry hashes, slots/counts/text hashes came from repaired JS and are never regenerated by a C# test. shared-goldens.mjs default is verify-only; --create refuses if manifest already exists. Negative duplicate/path/malformed/DTD goldens are byte-bound as well. Native adds strict XML validation of every XML part and OPF checks beyond readHwpxPackage's raw inventory; validateManifest=false is an explicitly limited inventory mode, not a claim that a missing manifest is valid HWPX. Native control-character/JSON duplicate-key handling is also intentionally fail-closed. These are documented extra guards, not an unqualified claim that every parser input has identical acceptance semantics.

Recovery checks jindan-engine-recovery/1 schema, outer reportReady=false/project-assisted mode, project/hash,1..1000 record IDs, roles, entry names, sizes/hashes, parents/missing parents/self-links/cycles, native-saved fresh-analysis requirement, unregistered entries,512MiB input/520MiB expanded/8MiB manifest and finite JSON/64-level nesting/prototype keys. It returns only an inventory, never recovered old review approval or mutable state. SHA gives integrity, not user/publisher authentication. Fresh reanalysis/review remains the host+JS boundary; native-saved is always RequiresReanalysis=true. No standalone metadata preservation is inferred.

Run from the new root after setting all safe process-local SDK variables (including DOTNET_GENERATE_ASPNET_CERTIFICATE=false):

```powershell
node tests/Jindan.NativeEngine.Tests/shared-goldens.mjs
& ./.tools/dotnet/dotnet.exe run --project tests/Jindan.NativeEngine.Tests/Jindan.NativeEngine.Tests.csproj --no-launch-profile
```

No original/company report, native Hancom process, cloud, settings, font installation or live data is used. reportReady=false and supervisorAccepted=false remain.

## Two genuine local gaps repaired

`F:/jindan/src/components/DashboardGallery.jsx` and `src/services/galleryData.js` render at most eight mixed image/CAD items from authorized Drive metadata, sorted by Drive modifiedTime. The new Dashboard previously had no preview strip. `src/Modules/Dashboard/DashboardGallery.cs` now owns up to eight scoped local tiles, bounded asynchronous thumbnails, explicit refresh and an exact clicked-photo preview. Opening re-queries the record/revision/asset linkage and re-authorizes the immutable asset; context changes close only owned preview windows and discard pending results. Damaged/locked/unsupported images get a visible fallback; original bytes are untouched. CAD tiles re-authorize then pass the existing owned asset path through the optional source-opening capability. Files resolves that authorized project asset without importing another copy, navigates the registered folder, selects its exact revision through the normal guarded editor/paging/event path, rechecks it and opens the bounded local CAD preview. Arbitrary local paths, dirty navigation, stale revisions and cross-project paths are rejected.

The local record contract has no reliable cross-kind `modifiedTime`. The label explicitly says **local registry reverse order by kind**, not Drive recency. EXIF capture time, random IDs and filesystem timestamps are not invented as authoritative remote recency. Real remote modified ordering requires actual provider metadata. The separate Photos gallery continues to own zoom/pan/previous/next and edited-copy export; Dashboard supplies a fit preview. Neither window replaces the original file.

Image-format scope is narrower than a browser: native Photos imports JPEG/PNG/BMP/GIF/TIFF and uses the available Windows decoder. Dashboard can list WebP/AVIF metadata but shows a visible fallback when that decoder cannot read it. Native WebP/AVIF Photos import and browser codec fidelity are not implemented or approved by these PNG-based tests; no codec was installed and no original image was converted or replaced. This is an explicit format difference, separate from the tested scoped preview/navigation behavior.

`ProjectWrite.jsx` actually provides bold/italic/underline and `BoardWrite.jsx` also character and paragraph styling. Therefore previous plain-text-only native editing was a real local feature difference. Projects and Board now use `RichTextEditor70`, with an optional `contentRtf` companion and the original plain `content` remaining authoritative. Native toolbar operations include bold/italic/underline/strike, size/font, foreground/background, left/center/right, bullets, quote indent and literal horizontal separation. Board threads safely render validated formatting. The raw companion is hidden from the list.

`RichTextRules70` enforces length/UTF-8/depth/control-word/numeric bounds and derives the text for exact normalized correspondence. Objects, images, fields, file references, binary payload, HTML and unknown destinations are rejected before stored RTF is loaded. Pasting only reads plain Unicode text, never writes the clipboard and never launches a URL. Formatting remains optional; plain records and literal historical HTML bytes remain literal text, without silently executing or migrating old HTML. This implements native character/paragraph formatting; it does not claim arbitrary legacy HTML/CSS rendering, active hyperlinks or browser justification fidelity. Installing fonts, Hancom manipulation and a browser security exception are not needed.

The R6 `SelectionChanged` **and** `CurrentCellChanged` binding hooks, dirty selection restoration and photo fixes remain in place. The rich editor change has its own formatting-only dirty notification, and invalid edited RTF blocks Save rather than saving an earlier hidden value.

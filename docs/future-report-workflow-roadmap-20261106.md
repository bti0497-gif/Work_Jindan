# 보고서 분석과 현장 조사 준비 개발 로드맵 초안

작성일: 2026-11-06. 상태: 추가 검토 중.

당장의 개발 우선순위는 **Drive 파일관리와 Firebase 게시판 연결**이다. 아래 보고서 분석·파트 배분·현장 조사 준비 흐름은 검토용으로 보관하고, 로드맵을 확정한 뒤 필요한 시점에 AI 연동을 진행한다. 현재 AI API 연결, 모델 설정, 키 등록, ChatGPT 로그인 연동은 진행하지 않는다.

여기서 보류하는 API는 보고서 분석을 위한 **AI API**를 뜻한다. Drive와 Firebase 연결에 필요한 서비스 인터페이스는 당장의 연동 범위에 포함한다. 이 문서는 실제 계정 연결이나 클라우드 쓰기를 수행한 결과가 아니다.

## 당장 진행할 Drive와 Firebase 연결

| 대상 | 연결할 기능 | 먼저 확인할 사항 |
| --- | --- | --- |
| Drive 파일관리 | 프로젝트별 폴더·파일 조회, 필요한 파일 내려받기, 파일 등록과 관리, 캐시와 연결 상태 표시 | 기존 폴더 구조, 사용자 인증, 공유 드라이브 여부, 실제 접근 권한, 중복 파일 정책 |
| Firebase 게시판 | 기존 게시판 목록·본문 조회, 작성·수정·삭제, 첨부파일과 작성자 연결 | 실제 게시판 컬렉션과 필드, 인증·보안 규칙, 작성자·프로젝트 접근 범위, 첨부 저장 위치 |
| 공통 | 로그인과 프로젝트 문맥 연결, 오류·오프라인 상태, 재실행 후 복구 | 로컬 사용자와 외부 계정의 대응, 권한 변경, 재시도와 충돌, 자격증명의 로컬 보호 |

기존 `F:/jindan`의 구현·규칙은 읽기 전용으로 확인하고 새 작업은 `F:/jindan-dotnet`에서 이어간다. 기존 환경파일·토큰·로그인 세션을 그대로 복제하지 않는다. 최초 연결에서 기존 자료를 자동 정리하거나 폴더를 임의 생성하지 않는다.

현재 로컬 파일관리·게시판 기능과 시험용 Drive 캐시가 있으며, 실제 Drive/Firebase 제공자는 연결되지 않았다. 프로젝트·공정·작업의 로컬 동기화 대기열도 **Firebase 게시판 연결과 별개**다. 게시판 스키마를 작업 동기화의 컬렉션 이름으로 추측하지 않는다. 자세한 현재 범위는 [Drive 구현 경계](drive70.md), [작업 동기화 경계](sync70.md)에 있다.

연동은 기존 서비스 구조 확인 → 인증과 데이터 계약 확정 → 실제 조회·다운로드 → 명시적 변경 작업 → 오류·권한·재실행 검사 순서로 진행한다. 이 우선순위가 보고서 AI 연동이나 모든 업무 데이터의 클라우드 동기화까지 자동으로 포함하는 것은 아니다.

## 미래 보고서 기능의 목적

전회 보고서를 충실하게 복원하는 기능에 더해, **이번 진단에서 무엇을 조사해야 하는지 먼저 파악**하고 그 결과로 빈 현장 조사 양식을 만들어야 한다. 그 다음에 수집한 금회 자료가 어느 본문·표·그림을 교체할지 연결한다.

사용자가 교체할 셀을 먼저 전부 선택해야만 조사 항목이 나오는 방식으로 끝내지 않는다. 전회 보고서에 대응 셀이 없더라도 필요한 현장 확인, 사진, 운전 기록, 담당자 질문을 근거와 함께 추가할 수 있어야 한다.

## 역할별 작업 흐름 제안

### 프로젝트 등록자와 분석자의 준비

1. 전회 보고서를 프로젝트에 등록한다. 원본 파일과 출처를 보존한다.
2. 이미 공정·기계·전기 또는 장별로 나뉜 보고서는 그 구분을 활용한다. 한 파일이면 장과 분야를 나누는 후보를 만든다.
3. 앱은 AI가 읽기 쉬운 구조로 파싱하고, 향후 연결될 AI에 장·분야 구분을 의뢰한다. 등록자가 결과를 검토해 확정한다.
4. PDF는 원문 구조를 분석해 편집 가능한 HWPX 복원본을 준비한다. 원본 HWPX가 있는 경우에는 그 자체를 분석 대상으로 보존한다. PDF 복원과 장별 패키지 생성의 상세 실행 순서는 추가 검토한다.
5. 확정한 장·분야 묶음을 Drive에 저장하고 담당 파트 또는 담당자를 배정한다.

등록자의 기본 역할은 보고서 등록·분할·배정까지다. 각 파트의 상세 조사 계획을 등록자가 모두 대신 작성하는 구조로 고정하지 않는다. 물리적으로 원본을 잘라 덮어쓰지 않고, 원본을 참조하는 별도 파트 패키지를 만든다.

### 각 파트 담당자의 분석과 조사 준비

1. 담당자는 자기 앱에서 권한이 있는 프로젝트·파트 목록을 Drive로 조회한다.
2. 맡은 분야의 보고서와 파싱 결과, 필요한 공통 시설·설계 정보를 내려받는다.
3. 자기 프로젝트·파트의 분석 문맥에서 AI에 조사 항목 분석을 의뢰한다.
4. 앱은 분석 결과를 원문 위치와 함께 보여 준다. 담당자가 필요한 측정·자료·사진·질문과 불확실한 내용을 확인한다.
5. 확정한 조사 목록으로 편집 가능한 빈 HWPX 양식을 만든다. 금회 측정값·판정은 공란으로 둔다.
6. 현장에서 양식을 작성하고 사진·운전 기록 등 근거 자료를 추가한다.
7. 작성본을 반환하면 필드 식별자, 원본 버전, 단위·기간·설비 대응을 검사한 뒤 보고서의 교체 대상과 연결한다.
8. 검증된 금회 자료로 해당 파트의 초안을 만들고, 검토 결과와 산출물을 Drive에 저장한다.

공통 자료나 복합 분야 내용은 필요한 파트에 함께 연결한다. 자기 파트만 내려받는 원칙 때문에 공학적 판단에 필요한 앞뒤 문맥을 잃어서는 안 된다.

### 프로젝트 종료

프로젝트별 분석 작업 세션과 임시 문맥을 정리한다. 확정 보고서, 조사 목록, 작성 양식, 수집 근거, 원본과 변경 이력은 보관 정책에 따라 유지한다. 프로젝트 종료가 다른 프로젝트의 로그인 해제나 모든 결과물 삭제로 이어지지 않게 한다.

## AI 전달용 파싱 계약 제안

AI의 주 입력은 관련 장의 내용을 충실히 담은 구조화 데이터로 한다. 짧은 요약만 보내거나 HWPX의 방대한 XML을 그대로 보내는 방식에 의존하지 않는다. 복잡한 도표는 필요한 원본 이미지도 함께 연결한다.

| 내용 | 보존할 정보 |
| --- | --- |
| 원문 식별 | 프로젝트·보고서·장·분야 식별자, 원본 버전과 SHA, 페이지·문단·표·셀·그림 위치 |
| 본문 | 제목 계층, 관련 본문 전체, 목록 구조, 각주와 참조 |
| 표 | 제목, 행·열과 병합 구조, 라벨·단위·주석, 과거 수치와 해당 기간 |
| 그림과 사진 | 개별 객체·캡션·라벨, 필요한 실제 이미지, 본문과의 연결 |
| 공통 문맥 | 시설·설비 식별, 설계 규격, 다른 파트에서 참조해야 하는 기준 정보 |
| 전송 범위 | 포함·누락한 장과 객체, 분할 순서, 완전성·추출 불확실성 표시 |

글자 수 제한 때문에 원문을 조용히 잘라 보내지 않는다. 장별로 나누되 관련 표·단위·주석을 함께 묶고, 누락 자료를 추가 요청할 수 있어야 한다. 디지털 원문 PDF를 기본으로 하며 OCR을 기본 복원 경로로 추가하지 않는다.

글꼴·여백·문단·객체 배치와 원본 XML·그림 자산은 앱의 복원 엔진이 관리한다. AI는 조사 항목과 분석 데이터를 정해진 형식으로 반환하며, 임의의 실행 코드나 HWPX XML을 생성 경로에 직접 주입하지 않는다.

## 분석 결과와 빈 양식 계약 제안

각 조사 항목은 조사 목적, 필요 이유, 담당 분야, 수집 방법, 대상 설비, 단위·기간·조건, 필수 여부, 원문 근거, 연결할 교체 대상, 불확실성을 갖도록 한다. 예를 들어 전회 수질 표를 근거로 금회 유입·방류 자료와 측정 기간을 요청하되, 과거 수치를 금회 양식의 값으로 채우지 않는다.

현황·문제점·개선대책과 비용 등 진단 의견은 실제 근거가 확보된 뒤 작성한다. 비율·효율·합계는 검증 가능한 계산 로직이 처리하고, AI가 만든 수치를 그대로 확정하지 않는다. 설계 상수, 명시적 과거 비교, 일반 관리 문구와 금회 측정·판정을 구분한다.

빈 양식의 필드에는 안정적인 식별자를 부여하고 반환 시 실제 원문 슬롯과 결합한다. 원본 변경, 다른 프로젝트 응답, 이미 교체된 입력, 오래된 분석 결과는 그대로 적용하지 않고 재검토한다. 기존 일부 셀의 JDF 반환 시험을 회사 전체 조사 양식의 완성으로 확대 해석하지 않는다.

## 분석 세션과 외부 AI 연결 검토

분석 문맥은 기본적으로 **프로젝트 × 분야 × 담당자**로 나누고, 필요하면 분석 목적과 원본 버전을 함께 식별한다. 담당자 변경, 장 추가, 응답 지연, 취소와 재시도 시 이전 결과가 다른 작업에 섞이지 않아야 한다.

앱의 분석 세션과 ChatGPT 웹사이트의 대화는 구분한다. 웹사이트의 로그인 쿠키를 추출·공유하거나 Drive에 인증정보를 저장하는 방식은 채택하지 않는다. 프로젝트 종료 시 앱에서 정리할 데이터와 외부 서비스에서 삭제할 수 있는 데이터의 범위도 별도로 확정한다.

AI 연결 방식은 **미정·보류**다. 향후 공식 로그인 연동 또는 API 방식의 제공 범위, 계정·앱 자격, 사용량·비용, 회사 자료 처리 조건을 다시 확인한다. 이미 브라우저에 로그인돼 있다는 사실만으로 앱에 호출 권한이나 무제한 사용량이 생긴다고 가정하지 않는다. 특정 모델이나 요금 경로도 지금 확정하지 않는다.

코드는 파싱·전달·식별자 결합·검증을 맡고 AI는 내용의 의미와 조사 필요성을 판단하도록 역할을 나눈다. 로컬 AI를 앱에 내장하는 것은 이번 제안의 전제가 아니다. 공학적 판단은 담당자의 검토를 거쳐 확정한다.

## 현재 구현과 앞으로 필요한 기능

| 구분 | 현재 범위 | 추가 개발·검토 |
| --- | --- | --- |
| 보고서 재현 | 기존 HWPX/PDF 분석·복원 경로와 제한된 실물 검증 이력 | 정확한 산출물별 서식·원본 글꼴·저장 보존·객체 편집 검증 |
| 내용 분석 | 구조 추출, 규칙 기반 역할 후보, 장·표·그림 등 목록 | 관련 장의 충분한 문맥으로 조사 필요성을 판단하는 의미 분석 |
| 분석 제안 교환 | 오프라인 요청·응답 검증과 명시적 적용 | 완전한 장별 패키지, 실제 AI 연결, 파트별 검토 흐름 |
| 빈 양식 | 선택한 입력·표 셀의 양식 생성과 식별자 기반 반환 | 보고서에서 조사 항목을 도출하고 전체 필요한 양식을 구성하는 흐름 |
| 금회 자료 | 일부 원시 셀의 근거 연결과 초안 차단 검사 | 분야별 실제 측정·사진·질문·기록의 수집과 검증·적용 |
| 협업 | 로컬 모듈과 시험용 계약 | 실제 Drive 배분·조회·변경, Firebase 게시판, 권한·동기화 |

현재의 오프라인 제안 교환과 보존 검사는 [보고서 구현 경계](report70.md)에 있다. 특히 기존 요청의 일부 요약·미리보기 필드를 장 전체를 충실히 전달하는 계약으로 간주하지 않는다. `reportReady=false`, `supervisorAccepted=false`를 유지한다.

여기서 실무 검증은 별도 형식적 회사 결재를 뜻하지 않는다. 필요한 기능을 구현한 뒤 실제 프로젝트 자료로 분석 누락, 현장 양식 사용, 반환·교체·초안의 정확성을 확인하는 단계다.

## 구현 순서와 완료 기준 제안

1. **현재 우선순위:** Drive 파일관리와 Firebase 게시판을 연결하고 기존 자료·권한·첨부·오프라인·재실행 동작을 검증한다. AI는 연결하지 않는다.
2. **로드맵 확정:** 등록자와 파트 담당자 역할, 공통 문맥, 배정·버전·보관 정책, 분석 요청·응답 계약을 사용자와 검토한다.
3. **보고서 패키징:** 장·분야별 원문 대응과 내용 완전성을 검증한다. AI 없이도 내보내기·검토·다시 불러오기가 가능하게 한다.
4. **AI 분석 연결:** 확정된 방식으로만 연결한다. 분야별 조사 필요성, 누락·불확실성, 출처 결합, 오래된 응답 차단을 검증한다.
5. **현장 조사와 반환:** 확정한 조사 목록에서 빈 양식을 만들고 실제 편집·저장·재열기·반환을 검증한다. 빈값은 빈값으로 유지한다.
6. **초안과 협업:** 검증한 금회 자료만 적용해 파트별 초안을 만들고 다운로드·보관·재실행·담당 변경을 검증한다.

각 단계는 구현 시험과 실제 문서 시험을 구분한다. 엔진은 파싱·복원·양식·반환 계약을 분리해 다른 PDF 앱에서도 재사용할 수 있게 유지하되, 별도 PDF 앱의 수정은 이 로드맵의 실행 범위에 포함하지 않는다.
